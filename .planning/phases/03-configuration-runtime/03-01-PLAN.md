# Phase 3 Plan: Configuration Runtime

**Status:** Complete
**Requirements:** CONFIG-01, CONFIG-02, CONFIG-03, CONFIG-04, QUAL-01, DOCS-03

## Goal

Make configuration management and switching a real application service with tested transactional semantics while
keeping host audio mutation clearly outside this phase.

## Tasks

- [x] Add core configuration CRUD helpers for create, rename/update, duplicate, delete, import, and export.
- [x] Add migration helpers that normalize older persisted payloads into the current schema.
- [x] Add a runtime transaction port and state machine for unload, apply, verify, and rollback.
- [x] Add tests for CRUD/import/export, migrations, startup re-apply planning, success, apply failure, and verify
  failure rollback.
- [x] Wire desktop UI controls for new, duplicate, delete, import, export, and transactional switching.
- [x] Update docs to describe configuration runtime behavior and current non-host-routing boundary.
- [x] Run project validation gates and capture evidence.

## Acceptance Criteria

1. Users can create, edit, duplicate, delete, export, and import configurations from the app shell.
2. Selecting a configuration executes the core runtime transaction path and persists only the verified target state.
3. Startup restore creates a verification transaction for the selected persisted configuration.
4. Invalid persisted or imported state falls back safely without corrupting current state.
5. Docs distinguish app-runtime transaction behavior from future host audio graph application.

## Risks

- It would be easy to overclaim routing because the runtime shape now has apply/verify/rollback. This phase must keep
  the adapter fake/app-local and documentation explicit.
- Import/export validation needs to reject malformed graphs without deleting the user's existing configurations.
- Deleting the active or final configuration must keep the state usable.
